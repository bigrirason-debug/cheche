## 좌석 1 · Architect (모듈 경계 · 의존 방향 · expect/actual · 포맷 버전)

1. `[H]` **PLAN v1과 D-020이 어긋난 채 착수 상태다.** → PLAN 헤더는 "근거 D-001~D-013", §4.1은 `spike-android/`·`spike-desktop/` 모듈, §5는 M0·M1 manual, §6은 A/B 시안 비교. D-020은 스파이크를 앱 내 Diagnostics 화면으로 흡수, 디자인 B 확정, 전면 auto, Android 타깃은 `-Pplaten.android=true`일 때만 구성이라고 결정. → `PLAN.md` 헤더를 "v1.1 — D-020 반영"으로 올리고 §4.1에서 `spike-*` 삭제·`ui/diagnostics` 추가, §5 M0 산출물을 "진단 화면 포함 APK + CI", §6을 "B안 DESIGN.md v1(시안 비교 없음)"으로 고친다.
2. `[H]` **`.strokes` 바이너리에 버전·레코드 길이가 없어 "모르는 필드 보존" 원칙이 바이너리에서 깨진다.** → §4.5는 `schema`/`minReader`를 manifest에만 두고 `pages/NNNN.strokes`는 "획 헤더 + float32 배열"로만 정의. 필드 추가(예: 후속 `orientation`, 지우개 분할 표시) 시 구독자가 구버전 파일을 오독한다. → §4.5에 `.strokes` 레이아웃을 명시: 파일 매직 + `formatVersion u16` + 획마다 `recordLength u32` + `sampleStride u8`(샘플당 float 수) + 필드 비트마스크. 리더는 stride로 모르는 채널을 건너뛴다.
3. `[H]` **단위가 둘이다(pt vs px).** → §4.5 "내부 좌표 pt(1/72in)", brush-formats §3.2 `size.base`는 "100% 줌 기준 지름(문서 px)", §4.4 성능 상한 "팁 ≤512px", `taper.length px`. 굿노트 132dpi 사실(§4.5)과 S9+ 266ppi 사이에 환산 정의가 없어 Android↔Windows 렌더 일치(§1.2 ≤2%)가 단위 해석 차이로 깨질 수 있다. → §4.5에 "문서 단위 1 = 1pt, 브러시의 px는 **문서 pt로 재정의**(`size.base` 단위 = pt)"라고 한 줄 못 박고 brush-formats §3.2 표의 "px"를 전부 pt로 바꾸는 DECISIONS 1건 추가.
4. `[M]` **`brush/`와 `core-ink/`·`core-render/` 사이에 순환 의존 위험.** → §4.1: `core-ink`가 "스탬프 배치", `core-render`가 "stamp 엔진", `brush/`가 "brush.json 모델 + 임포터 + 프리컴포즈(이미지 연산)". 스탬프 배치에는 브러시 모델이 필요하고 프리컴포즈에는 렌더/비트맵이 필요하다 → brush↔core-render 양방향. → `brush-model/`(commonMain 순수 데이터·커브 LUT·스키마)과 `brush-import/`(zip·bplist·abr·이미지 정규화)로 분리. 의존 방향: `core-model → brush-model ← core-ink ← core-render`, `brush-import → brush-model + 이미지 expect/actual`.
5. `[M]` **expect/actual 지점이 산발적으로만 적혀 있다.** → §4.1에 셰이더·pdf·auth만 명시. 누락: 이미지 디코드/인코드(팁 정규화, `thumb.png`), 보안 저장소(토큰), 파일 위치/SAF, 프론트버퍼 호스트, 시계·디바이스 ID. D-020 ⑤로 Android actual은 CI에서만 컴파일되므로 누락이 늦게 터진다. → §4.1 아래에 "expect/actual 목록 표(이름·commonMain 인터페이스·android/desktop actual·소유 단위)"를 추가하고, CI에 "PR마다 `-Pplaten.android=true`로 `compileDebugKotlinAndroid`만 실행"하는 잡을 넣는다.
6. `[M]` **`input/` 모듈 정의가 플랫폼 경계와 어긋난다.** → §4.1 `input/ androidMain`인데 내용에 "제스처 매핑 테이블 엔진(commonMain)"이 들어 있고, Windows 마우스/터치 올가미·핀치(A9, M6)는 어느 모듈인지 없다. → `input/`를 commonMain(정책·매핑 엔진·`PointerSample` 모델) + `androidMain`(MotionEvent 어댑터·프론트버퍼 호스트) + `desktopMain`(AWT 포인터 어댑터)로 재정의.
7. `[M]` **"결정적 zip = 같은 md5"는 압축기 구현에 의존한다.** → §4.5·sync-google §5-4. 엔트리 순서·타임스탬프 고정만으로는 deflate 출력 동일성이 보장되지 않는다(Android와 JVM의 zlib 버전 상이 가능, 추정). → 변경 감지 기준을 "zip 바이트 md5"가 아니라 manifest에 기록한 `contentHash`(엔트리별 비압축 SHA-256의 정렬 연결)로 바꾸고, Drive md5는 "원격이 바뀌었는가"(sync-google §5 1항) 판정에만 쓴다고 §4.6에 적는다.
8. `[L]` **젖은 잉크 경로가 GL/Canvas 둘로 열려 있다.** → §4.2 "LowLatencyCanvasView 또는 GLFrontBufferedRenderer". GL 경로면 `core-render`(Compose Canvas) 코드를 재사용할 수 없어 렌더 일치가 깨진다. → `CanvasFrontBufferedRenderer`/`LowLatencyCanvasView`(android.graphics.Canvas → Compose Canvas 래핑)로 고정하고 GL은 M0 대조군에서 제외.

**이 좌석이 가장 바꾸고 싶은 한 가지**: §4.5에 `.strokes` 바이너리 레이아웃과 단위(pt) 정의를 넣는 것 — 포맷은 나중에 못 고친다.

## 좌석 2 · Skeptic (실기기 없이 진행될 때 조용히 깨지는 것)

1. `[H]` **스택 전환 규칙은 실제로 발동할 수 없다.** → §3 전환 규칙은 M0 실기기 결과(M1·M2·M6·M10)에 걸려 있는데 D-020 ①은 "실기기 게이트는 진행을 막지 않음". 사용자 측정이 M5 이후에 도착하면 그때는 이미 Compose UI·commonMain이 쌓여 있어 C(WinUI 3 C#)로 전환하면 브러시 파서·동기화·포맷을 C#으로 다시 쓴다(stack.md §4 대안 1 비용). → §3을 "전환 결정 시점 = **첫 실기기 측정표 도착 시**, 그때까지 각 M의 실기기 항목은 `[미측정]` 배지 유지. C 전환 범위는 `app-desktop`+`ui` Windows 계층만이며 공통 모듈은 JVM으로 유지한다(즉 C는 '전체 스택 전환'이 아니라 'Windows 셸 전환')"로 다시 쓴다.
2. `[H]` **"검증했다고 착각하기 쉬운 지점" 목록** (각각 §5 검증 방법 열에서 근거):
   - M2 "1만 획 p95 ≤8.3ms(실기기)" — 컨테이너에서 측정되는 것은 Desktop JVM뿐. Android 수치는 0건.
   - M2·M6 "골든 PNG" — Android 타깃은 로컬에서 빌드되지 않고(D-020 ⑤) CI에도 기기가 없으므로 **Android 렌더러는 사용자가 APK를 열기 전까지 한 번도 실행되지 않는다**. M11 "Android↔Windows diff ≤2%"는 Android PNG 덤프가 없어 측정 불가.
   - M3 "합성 샘플로 구조 테스트" — 파서가 자신의 가정으로 만든 샘플을 읽는 순환 검증. Procreate 실파일 키 층위(brush-formats §1.4 A/B/C)는 검증되지 않는다.
   - M7 "모의 Drive 서버" — 같은 저자가 같은 가정(md5 의미, `drive.file` 가시성 R4)으로 쓴 목. R4는 목으로 재현 불가.
   - M4 "Compose semantics 테스트" — 접근성 이름 존재는 확인되지만 TalkBack 순서·호버 툴팁 동작은 아니다.
   - M6 `.msi` — windows-latest에서 **빌드만** 하고 실행하지 않으면 jlink 모듈 누락·Skiko D3D 초기화 실패가 사용자 설치 때 처음 드러난다.
   → §5 표에 "증거 등급" 열 추가: `CI-자동` / `CI-실행(윈도 러너에서 앱 구동)` / `실기기-대기`. windows-latest 잡에 "앱 헤드리스 기동 → 골든 렌더 → 종료" 스모크를 필수로 넣는다(러너에 GPU 없음 → 소프트웨어 렌더 폴백 결과임을 명시).
3. `[M]` **M10(Windows 터치) 합격선은 공허하게 통과될 수 있다.** → A9 "Windows 노트북은 터치스크린 없을 수도". 터치가 없으면 "터치 제스처 100%"는 측정 불가 = 불합격도 아님. #5278은 터치패드에선 정상(stack.md §3-1). → stack.md §5-3 M10을 "마우스만으로 올가미·페이지·핀치(Ctrl+휠) 100% + p95 ≤16.7ms"로 바꾸고 터치는 "있으면 기록".
4. `[M]` **commonMain에 JVM 전용 API가 스며든다.** → D-020 ⑤로 로컬은 "JVM(desktop)+common"만 빌드. android+jvm 두 타깃이면 중간 소스셋에서 `java.*`가 보이는데 `java.awt`·`javax.imageio`는 Android에 없다 → 컴파일은 CI에서, 크래시는 사용자 기기에서. → §4.1 규칙 한 줄: "공유 코드에서 `java.awt`/`javax.imageio`/`java.nio.file.Files` 금지(detekt/grep 게이트), 이미지·파일은 expect/actual".
5. `[M]` **골든 이미지의 출처가 없다.** → §5 M2 "골든 렌더 테스트 통과". 렌더러 첫 실행 출력을 골든으로 저장하면 아무것도 검증하지 않는다. → `tools/golden/`을 두 종류로: (a) 해석적 골든(일정 필압 직선 = Skia `drawLine` round cap과 픽셀 동일, 원형 스탬프 1개 = `drawCircle`) (b) 스냅샷 골든은 사용자 실기기 체크리스트에서 "승인" 후 잠금.
6. `[M]` **오프라인 우선이 M2~M6에서 보장되는지 확인 항목이 없다.** → §4.6·BRIEF §2b "오프라인 우선"인데 §5에 "로그인 없이 전 기능" 기준이 없다. M7은 사용자 OAuth 숙제에 전적으로 막힌다(sync-google §8.2 L1~L3). → M2 완료 기준에 "계정 없이 생성·편집·저장·내보내기 전부 동작"을 추가하고, `sync/`를 M3부터 **파일시스템 백엔드**(로컬 폴더 = 가짜 Drive)로 먼저 돌린다.
7. `[L]` **"크래시 0(1시간 사용)"·"팜 20회"는 사용자만 할 수 있다.** → §5 M4·M8. → 그대로 두되 "실기기-대기" 배지와 함께 "미측정 상태로 1.0 태그 금지"를 §8에 명시.

**이 좌석이 가장 바꾸고 싶은 한 가지**: §5 표에 증거 등급 열을 넣고, Windows 러너에서 앱을 **실행**하는 스모크를 M2부터 필수로.

## 좌석 3 · Performance / Input

1. `[H]` **§1.2 프레임 합격선이 측정 가능하게 정의돼 있지 않다.** → "프레임 p95 ≤8.3ms, 드롭 ≤5%"에 측정 지점(Choreographer 콜백 간격? `FrameMetrics.TOTAL_DURATION`? GPU 완료?)·측정 창·입력 시나리오가 없다. 손으로 하는 팬/줌은 매번 다르다. → §1.2 각 행에 "측정 정의" 열 추가: Android = `FrameMetrics TOTAL_DURATION`(일반 경로)·프론트버퍼는 `renderFrontBufferedLayer` 제출→`onFrameComplete` 간격; Desktop = Skiko 프레임 콜백 간격(API 존재는 추정, M0에서 확인); 시나리오 = 진단 화면의 **스크립트 제스처 재생**(고정 경로 10초)으로 빌드 간 비교 가능하게.
2. `[H]` **지연 지표가 "펜 다운→첫 픽셀"뿐이다.** → stack.md §5-3 M1. 사용자가 체감하는 것은 이동 중 펜촉-잉크 끝 간격(궤적 지연)이며 예측(M8)이 영향을 주는 것도 이것이다. 터치다운 지연은 프론트버퍼 on/off 차이만 드러낸다. → M1b 추가: "240fps 슬로모에서 일정 속도(약 15cm/s) 직선 긋기 중 펜촉-잉크 끝 거리(px) 중앙값, 삼성노트 동일 조건 대비 ≤1.5배".
3. `[M]` **240Hz 입력과 Compose 포인터 파이프라인의 충돌이 설계에 없다.** → §4.2는 `motionEvent` 히스토리 + `requestUnbufferedDispatch`를 함께 쓴다. 언버퍼드 디스패치는 배칭을 끄므로 `historySize`가 0에 가까워지고 이벤트 수가 240/s가 된다 — 이벤트마다 Compose 포인터 디스패치 + 프론트버퍼 렌더를 메인 스레드에서 하면 4ms 예산. 또 `PointerInputChange.historical`에는 필압이 없다(stack.md §3-1). → M0/진단 화면에서 두 경로를 비교 측정: (a) Compose `pointerInteropFilter` (b) SurfaceView 호스트의 `onTouchEvent`에서 직접 수신(캔버스 영역만 Compose 포인터 시스템 우회). M2 입력 Hz 계산식을 "이벤트 수 + 히스토리 수"로 명시.
4. `[M]` **스탬프 엔진 상한은 있으나 프레임당 예산과 증분 갱신 규칙이 없다.** → brush-formats §3.7: D=512·spacing 0.03·40cm/s → 약 280 stamps/s × 262k px ≈ 73Mpx/s. 젖은 잉크를 매 이벤트 전체 재그리기하면 상한 안에서도 터진다. → §4.4에 "프론트버퍼는 **새 스탬프만** 증분 그리기(damage rect), 스탬프 수 상한 = 프레임당 64, 초과분은 다음 프레임으로 이월(시각적으로 테이퍼 끝만 늦음)"을 적고 §1.2에 "스탬프 브러시 512px·3%에서 드롭 ≤5%"를 측정 정의와 함께.
5. `[M]` **1만 획 타일 캐시 전략이 이름만 있다.** → §4.1 "타일 캐시". 타일 크기·줌 변경 시 재래스터 정책·메모리 상한·레이어 수(형광펜 아래 레이어 + 잉크 = 최소 2층, typewriter-refs §7.2)·로드 시 지오메트리 재계산(§4.3 "캐시는 파생물") 비용이 없다. 30점×1만 = 30만 샘플의 외곽선 생성은 로드 시간에 직접 든다. → §4.1에 캐시 스펙 1단락(타일 512px², 줌 단계별 LOD 2단, 메모리 상한 = 화면 4배, 페이지 단위 LRU, 레이어 2) + §1.2에 **로드 시간 합격선**(1만 획 노트 열기 → 첫 페이지 표시 ≤1.0s, 추정치이므로 M2에서 보정).
6. `[M]` **다크 모드 재매핑·블렌드 전환이 배칭을 깬다.** → §4.1 "다크 모드 색 재매핑, 형광펜 혼합", typewriter-refs §7.2 Screen/아래 레이어. 획마다 블렌드 모드가 바뀌면 드로우콜이 쪼개진다. → 형광펜(및 `blend=multiply` 브러시 전부)을 **별도 레이어**에 모아 레이어 단위로 블렌드를 적용하는 것을 §4.1 캐시 스펙에 포함(성능과 가시성 요구를 한 번에 해결).
7. `[L]` **"필압 고유값 ≥1,024"는 노이즈로도 통과한다.** → stack.md M3. float 필압은 고유값이 쉽게 늘어난다. → "고유값"이 아니라 "정렬 후 인접 차이의 최빈값 ≤1/1024"로 바꾼다.
8. `[L]` **Windows p95 ≤16.7ms는 D3D 전제인데 러너·VM에선 소프트웨어 렌더다.** → stack.md §5-2 Desktop 3 "Direct3D 기본, OpenGL/Software 비교 토글". → CI 스모크 수치는 "소프트웨어 렌더 참고값"으로 분리 기록하고 합격 판정에 쓰지 않는다.

**이 좌석이 가장 바꾸고 싶은 한 가지**: §1.2에 "측정 정의" 열(지표 소스·시나리오·창)을 넣고 진단 화면에 스크립트 제스처 재생을 넣는 것.

## 좌석 4 · Security / Privacy / Legal

1. `[H]` **임포트 파서 방어 상한이 PLAN에 없다.** → §4.4는 성능 상한(팁 ≤512, spacing ≥0.03)만. brush-formats §3.5 "4096px 초과 헤더 거부"와 §7 "바운드 ≤8192"가 있지만 zip 폭탄(엔트리 수·비압축 총량·헤더 `size` 불신), zip 경로 탐색(`../`), bplist 오프셋 테이블 범위·객체 수·UID 순환(깊이 제한만 언급), ABR `samp` 길이 vs 잔여 바이트·RLE 행 길이 오버플로·디스크립터 재귀 깊이, PNG 헤더 거짓말(디코드 할당 상한)이 없다. `.platen` 자체도 Drive에서 내려오는 **신뢰할 수 없는 zip**이므로 같은 규칙이 적용된다. → §4.4에 "임포트 방어 상한 표" 추가: 엔트리 ≤2,000, 엔트리 비압축 ≤64MB(카운팅 스트림으로 강제), 총 ≤512MB(스트리밍, 전체 메모리 적재 금지), 경로 정규화 후 루트 밖 거부, plist 객체 ≤100k·깊이 ≤64, 이미지 픽셀 ≤4096²·디코드 전 바운드 조회, ABR 바운드 ≤8192·RLE 행 길이 ≤너비×2, 디스크립터 깊이 ≤32. CI에 변이 퍼저(샘플 바이트 뒤집기 1만 회, 예외 외 크래시/OOM 0)를 넣는다. dd-plist는 외부 파서이므로 퍼저 대상에 포함.
2. `[H]` **데스크톱 리프레시 토큰 저장 방식이 정해져 있지 않다.** → §4.6은 라이브러리만 명시. sync-google §1.3: JVM `TokenStore` 기본은 메모리, .NET 관례는 평문 파일; DPAPI/Credential Manager는 "권장(추정)". KMP/JVM에는 DPAPI가 없다. → §4.6에 "Desktop: 리프레시 토큰은 Windows DPAPI(JNA 경유, **신규 의존성 → §9 추가 승인**) 또는 차선으로 사용자 전용 ACL 파일 + 문서화된 위험. Android: `AuthorizationClient` 액세스 토큰만 메모리 보관, 영속 저장 없음(추정, M7에서 확인)"을 명시.
3. `[M]` **데스크톱 client_secret이 CI 아티팩트에 구워진다.** → §9 CI Secrets에 `PLATEN_DESKTOP_CLIENT_SECRET`, 산출물은 GitHub Actions Artifacts(§5). 리포 가시성이 공개라면(추정) 아티팩트를 받은 누구나 시크릿을 추출한다(기밀성은 낮지만 sync-google §1.2 "커밋 금지" 취지에 반함). → 데스크톱 클라이언트 JSON은 **사용자가 첫 실행에서 파일로 지정**(사용자 = 개발자 1인). ## 좌석 5 · UX / Accessibility (타자기 은유 + 도구 앱)

1. `[H]` **설정 화면 과부하.** → A10 + §4.3 2층(전역 + 브러시별 오버라이드) + §4.2 매핑 테이블(입력 6 × 동작 8) + 다크 2종(크롬/종이) + 예측·손가락 필기·팜 + 레이저·표 기본값 + UI 밀도·종이 색·기본 펜. 컨트롤 30개 이상이 한 화면에 몰리고 "굵기"를 바꿀 수 있는 곳이 3곳(슬롯·브러시 시트·전역)이 된다. → §4.8에 설정 IA 고정: 그룹 3개(필기 / 입력·제스처 / 화면)로 각 그룹 "기본값 복원" 1개; 전역 필기 슬라이더는 필압·스무딩·테이퍼 3개만 노출하고 커브 편집기는 "고급" 접기; **브러시별 오버라이드는 전역 설정에 두지 않고 펜 재탭 시트에서만**, 시트는 유효값과 출처 배지(전역/브러시)를 보여 준다.
2. `[H]` **마진 스톱이 상시 드래그 핸들로 툴바에 있으면 오조작·공간 비용이 크다.** → §4.8 "툴바 프레임 + 눈금자 위 마진 스톱 마커 2개", typewriter-refs §1 "빨간 삼각 마커 2개". 여백·줄 가이드는 속지 속성이지 매 획마다 쓰는 도구가 아니다. 48dp 타깃(§1.2)을 가진 핸들 2개가 도구 아이콘과 한 줄에 있으면 손바닥·펜 호버 중 오드래그가 난다. → "마커는 평소 **정적 표시**(장식 아님, 현재 여백을 보여 줌), 눈금자 탭 → '속지 모드'에서만 드래그 가능. 접근성: 역할 slider, 값 텍스트('왼쪽 여백 24pt'), Windows 키보드 ←/→ 조절"을 §4.8에 명시.
3. `[M]` **2색 리본 토글과 색 슬롯 체계가 경쟁한다.** → §4.8 "펜 검정/빨강 즉시 토글", feature-matrix §1 제안 "색 3~12슬롯". 둘 다 있으면 토글은 중복이고, 토글만 있으면 파랑을 쓰는 사용자가 막힌다. → "리본 토글 = 사용자가 지정한 **리본 2색**(기본 검정/빨강) 간 1탭 교대, 슬롯은 별도 유지, 리본 색은 슬롯 중 2개를 지정"으로 의미를 §4.8에 고정.
4. `[M]` **다크 모드 규칙이 형광펜에만 있고 PDF·multiply 브러시엔 없다.** → §4.1 "다크 모드 색 재매핑, 형광펜 혼합"; typewriter-refs §7. 임포트한 Procreate 브러시의 `blend=multiply`는 어두운 종이에서 보이지 않고, PDF 배경(흰 페이지)은 "종이 다크"와 충돌한다. → "`blend=multiply` 브러시 전부에 형광펜 규칙 적용; PDF 배경 페이지는 종이 다크 비적용(크롬 다크 + 종이 라이트로 자동 전환, 'PDF 스마트 반전'은 후속)"을 §4.1·§4.8에.

## 의장 · 교차검토와 판정

### 충돌 조정
- **성능(좌석3) vs 보안(좌석4) — 임포트 상한**: 팁 ≤512px·4096² 디코드 거부·스트리밍 압축 해제는 둘 다에 이롭다. 충돌은 "큰 브러시셋(수백 개 × 2048² PNG)"뿐 → 엔트리당 64MB·총 512MB **스트리밍** 상한(메모리 적재 금지)으로 둘 다 만족. 채택.
- **아키텍트(좌석1) vs 스켑틱(좌석2) — 스택 전환**: 좌석1은 공통 모듈 보존을, 좌석2는 규칙의 무효를 지적. 조정: C는 "Windows 셸 전환"으로 범위를 좁혀 둘 다 성립(공통 모듈 JVM 유지 + 실제로 발동 가능한 규칙).
- **성능(좌석3 #3 Compose 포인터 우회) vs 아키텍트(좌석1 #6 input 모듈 경계)**: 우회 여부는 M0 측정으로 정하고 모듈 경계는 어느 쪽이든 수용하도록 `androidMain` 어댑터 안에 가둔다. 강제 규칙으로는 채택하지 않음.
- **보안(좌석4 #3 첫 실행 JSON) vs UX(좌석5)**: 첫 실행 마찰이 늘지만 사용자 = 개발자 1인이고 OAuth 클라이언트 생성이 어차피 사용자 숙제라 수용.
- **UX(좌석5 #4 PDF 종이 라이트 강제) vs BRIEF §4 "검정 잉크 자동 반전"**: PDF 페이지는 잉크 반전만 적용하고 배경은 원본 유지(크롬 다크) — BRIEF와 모순 없음.

### 기각 목록
- **테셀레이션(외곽선) 결과를 파일에 영속**(feature-matrix 원리 3의 절반): 파일 크기·스키마 변동 비용이 크고 §4.3 "재계산 가능" 원칙과 충돌. 대신 양 플랫폼 `kotlin.math` 동일 코드 + 해석적 골든으로 결정성을 검증한다(좌석1 #2의 리더 규칙으로 충분).
- **dd-plist를 자체 파서로 대체**(좌석4 #1의 극단안): 의존성 1개 줄이는 대가로 bplist 구현 비용과 새 버그. 퍼저 대상에 넣는 것으로 갈음.
- **캔버스 입력을 Compose 포인터 시스템에서 무조건 우회**(좌석3 #3): 측정 전 강제는 과하다. M0 비교 항목으로만.
- **리본 토글 제거**(좌석5 #3의 한 선택지): BRIEF 2b 확정 은유. 의미를 고정해 유지.
- **M8 "크래시 0·팜 20회"의 자동화 대체**: 대체 불가. 배지로만 관리.
- **C 대안 완전 삭제**: 발동 범위를 좁힐 뿐, 문서상 대안은 남긴다(R1).

### 마일스톤 순서 변경 제안
- **M6(Windows)의 "열람·렌더" 절반을 M2로 당긴다.** 근거: 렌더 일치(D-009)는 스택 리스크 1순위인데(§3), 컨테이너와 CI에서 **실제로 실행 가능한 유일한 플랫폼이 Desktop**이다(좌석2 #2). M2 산출물을 "APK + 같은 `.platen`을 여는 Desktop jar/스모크"로 바꾸면 commonMain 렌더러가 첫 마일스톤부터 두 타깃에서 돈다. M6는 편집 기능(올가미·페이지·텍스트·이미지·msi 패키징)만 남는다. 비용: 중(CI 잡 1개 + 최소 뷰어 셸).
- **M1은 D-020 ③으로 이미 축소**(B안 확정) → "DESIGN.md v1 + 토큰 대비표 + 컴포넌트 목록"만 남기고 M2와 병렬 진행(U5는 토큰만 선행하면 됨).
- **`sync/` 코어를 M3부터 파일시스템 백엔드로 선행**하고 Drive 어댑터만 M7에 남긴다(좌석2 #6). M7은 사용자 OAuth 숙제에 의존하므로 순서는 유지하되 M7의 "직렬 큐·충돌 사본·100회 폭주"는 M5까지 로컬 백엔드로 통과시킨다.

### 전체 판정: **수정 후 착수**
PLAN v1의 스택·모듈·포맷·동기화 골격은 리서치 근거와 맞고 재작성할 이유는 없다. 그러나 D-020과의 불일치, `.strokes`·단위 정의 부재, 측정 불가능한 합격선, 임포트 방어·토큰 저장 공백은 코드가 쌓이기 전에 고쳐야 하는 종류라 그대로 착수하면 포맷과 CI 증거 체계를 나중에 되돌려야 한다. 채택 권고 1·2·3·4·5(비용 낮~중, 반나절 분량 추정)를 반영한 v1.1로 U1·U3부터 착수하고, 6~10은 해당 모듈(U4·U5·U6) 착수 전까지 반영하면 마감(D-020 10-25 12:50 KST)과 충돌하지 않는다.
